# Pacer — 팀 과제·마감 코치 에이전트

팀 리더가 맡긴 과제를 작은 단계와 중간 마감으로 나눠 담당자에게 전달하고, 매일 체크인으로 진행을 확인하며 응원과 피드백을 주고, 막힌 일과 마감 위험만 팀 리더에게 요약해 알려 주는 Discord 봇.

기획안: https://gist.github.com/tnsgud/f42aedc07cec4f9c0183602534c5818d

## 사용 방법

Discord에서 `/도움말`을 치면 아래 내용을 요약해서 본인에게만 보여 줍니다. 팀 리더에게는 리더용과 담당자용 안내가 함께, 담당자에게는 담당자용만 나옵니다. 봇 DM에서도 쓸 수 있습니다.

### 시작 전에 (담당자)

- 봇이 있는 팀 서버에 들어와 있어야 합니다.
- 그 서버의 **개인정보 설정에서 "서버 멤버가 보내는 다이렉트 메시지 허용"을 켜 주세요.** 꺼져 있으면 과제와 체크인 DM을 받을 수 없습니다.

### 하루 흐름 (평일만, 한국 시간)

| 시각 | 누구에게 | 내용 |
| --- | --- | --- |
| 09:00 | 담당자 | 과제마다 오늘 할 단계, 목표일, 최종 마감까지 남은 영업일. 마감이 빠듯하거나 단계 목표일이 지났으면 경고 |
| 09:00 | 팀 리더 | 팀 과제 현황 (막힘 · 응답 없음 · 주의 · 순조로움) |
| 16:00 (금) | 팀 리더 | 주간 리포트: 과제별 완료율, 자주 막힌 단계, 체크인 응답률 |
| 17:00 | 담당자 | 체크인: "오늘 단계는 끝났나요?" + [완료] [진행 중] [막힘] |

**근무 시간(기본 평일 09:00~18:00) 밖에 생긴 알림은 소리 없이 갑니다.** 새 과제 전달, `/과제수정`, 마감 변경 요청·승인·거절, 막힘 전달처럼 누가 무언가를 해서 생긴 DM은 Discord의 @silent 메시지로 보내서, DM 창에는 들어가지만 휴대폰 알림이나 소리는 나지 않습니다. 담당자가 이런 DM을 받았으면 다음 아침 안내 첫 DM 맨 위에 "📝 어제 퇴근 뒤 바뀐 일정·알림이 있어요"가 한 번 붙습니다. 팀 리더에게 가는 DM도 같은 규칙입니다. 근무 시간은 `.env`의 `WORK_START`, `WORK_END`로 바꿉니다.

주말에는 보내지 않습니다. 낮에 `/완료`나 `/막힘`을 썼어도 저녁 체크인은 갑니다(새 단계에서 막혔는지 하루 한 번은 확인).

### 팀 리더

**과제 맡기기: `/과제`** (팀 서버 채널에서)

1. `/과제`를 입력하고 `담당자`(사람 선택), `내용`(과제 설명), `마감`(`2026-11-13` 형식)을 채웁니다. 같은 과제를 여러 명에게 시키려면 선택 항목 `담당자2`~`담당자4`도 채웁니다(최대 4명, 같은 사람·봇 계정은 빠짐).
2. 잠시 뒤 AI가 만든 단계 초안이 **본인에게만** 보입니다. 맨 위에 입력한 원문이 함께 나옵니다.
3. 초안 아래 버튼을 고릅니다.
   - **[이대로 전달]**: 담당자에게 과제와 단계를 DM으로 보냅니다. 담당자가 여럿이면 이때 사람마다 같은 과제가 따로 만들어지고, 이후 체크인·완료·현황은 사람별로 따로 진행됩니다. DM을 못 보낸 사람이 있으면 알려 줍니다.
   - **[수정]**: 입력창에서 제목, 최종 마감, 단계를 직접 고칩니다. 단계는 한 줄에 하나씩 `제목 - 2026-11-05` 형식입니다. 줄 순서가 단계 순서이고, 최종 마감보다 늦은 날짜는 받지 않습니다. 고친 뒤 다시 [이대로 전달]을 누르면 됩니다.
   - **[취소]**: 초안을 지웁니다. 담당자에게는 아무것도 가지 않습니다.

**전달한 과제 고치기: `/과제수정`** (팀 서버 채널에서)

진행 중인 과제가 버튼으로 나오고(과제 제목 · 담당자), 고르면 수정 입력창이 뜹니다. 제목, 최종 마감, **남은 단계**만 고칠 수 있고 이미 끝낸 단계는 그대로 둡니다. 저장하면 담당자에게 **바뀐 점**(최종 마감·제목 변경, 단계 목표일 변경, 이름 변경, 새 단계, 빠진 단계)과 남은 단계 목록이 DM으로 갑니다. 목록에서 바뀐 단계에는 ✏️, 새 단계에는 🆕가 붙고, 순서만 바뀐 것은 따로 적지 않습니다. 팀 리더 쪽에도 같은 바뀐 점이 표시됩니다. 바뀐 게 없거나 형식이 틀리면 아무것도 저장하지 않고 담당자에게도 알리지 않습니다. 마감 변경을 승인했을 때 담당자 DM도 같은 형식입니다. 여러 명에게 복사된 과제는 사람마다 따로 고쳐야 합니다.

**현황 보기: `/현황`** (팀 서버 채널에서)

진행 중인 과제를 막힘 · 응답 없음(영업일 2일 이상 체크인 없음) · 주의(마감 위험 또는 단계 목표일 지남) · 순조로움으로 묶어 본인에게만 보여 줍니다. 항목마다 진행 단계, 마지막 체크인, 마감 위험 근거("남은 단계 2개, 남은 영업일 1일")가 붙습니다.

**주간 리포트: `/주간리포트`** (팀 서버 채널에서, 금요일 16:00에는 DM으로도 옴)

이번 주(월요일~오늘) 기준입니다.
- **과제별 완료율**: 진행 중인 과제와 이번 주에 끝난 과제. 끝낸 단계 수/전체, 이번 주에 끝낸 단계 수, 마감 위험이면 근거.
- **자주 막힌 단계**: 이번 주 막힘 체크인을 "과제 › 단계"로 묶어 많은 순 5개. 같은 과제를 여러 명이 받았으면 합쳐서 셉니다.
- **체크인 응답률**(목표 80%, 성공 기준 중 이것만 주간 리포트에도 들어감): 사람별로 과제를 받은 뒤의 영업일 중 체크인한 날. 오늘은 이미 답했을 때만 셉니다(16:00 발송이 17:00 체크인보다 먼저라서).

**성공 기준 평가** (봇 밖에서, 도입한 사람이 확인)

기획안 섹션 5-2의 성공 기준은 봇을 도입한 사람이 "봇이 제 역할을 하는가"를 판단하는 평가 기준이라 Discord에는 보여 주지 않습니다. 봇은 필요한 기록만 쌓고, 결과는 터미널에서 봅니다. 운영 시작일부터 누적으로 계산해 목표와 비교합니다(✅/❌).

```bash
npm run metrics -- --since 2026-11-16          # 로컬 (since를 빼면 전체 기간)
docker compose exec pacer node dist/metrics.js --since 2026-11-16   # 서버
```

| 기준 | 계산 방법 |
| --- | --- |
| 초안의 80% 이상이 수정 1회 이내로 확정 | 전달한 초안의 [수정] 횟수. 여러 명에게 복사된 과제는 원본 하나만 셈. 전달 뒤 `/과제수정`은 넣지 않음 |
| 체크인 응답률 80% 이상 | 사람별로 과제를 받은 뒤의 영업일 중 체크인한 날 |
| 막힘 후 1영업일 이내 리더 인지 | 막힘 체크인 날부터 리더가 처음 안 날까지(전달 동의 DM, 아침 요약, `/현황`). 아직 1영업일이 안 지난 막힘은 빼고 셈 |
| 마감 놓친 과제 0건, 최소 2영업일 전 경고 | 마감이 지났는데 안 끝났거나 마감 뒤에 끝낸 과제. 그중 리더가 아침 요약·`/현황`에서 "주의"로 처음 본 날이 마감 2영업일 전 이상인 비율 |

"어디까지 했어?" 질문 횟수와 2주 후 설문은 봇 밖에서 직접 재야 합니다.

**운영 시작일을 `--since`로 꼭 넘기세요.** 빼면 테스트하던 기록까지 섞입니다.

**마감 변경 요청 받기**

담당자가 `/마감변경`으로 요청하면 DM으로 새 마감, 이유, 남은 단계와 [승인] [거절]이 옵니다. 대기 중인 요청은 `/현황`에도 "📅 마감 변경 요청 대기"로 보입니다.
- **[승인]**: 과제 마감을 바꾸고, 남은 단계 중 예전 마감에 맞춰 있던 단계와 새 마감보다 늦은 단계를 새 마감으로 옮깁니다. 단계 일정을 더 고치려면 `/과제수정`을 쓰세요.
- **[거절]**: 그대로 두고 담당자에게 알립니다.

**막힘 알림과 답장**

담당자가 막힘을 입력하고 **전달에 동의한 경우에만** 한 줄 요약이 DM으로 옵니다. 대화 원문은 오지 않습니다. 동의하지 않으면 현황에 "막힘" 상태만 보입니다.

- **[답장 보내기]**: 막힘 DM 아래 버튼을 누르고 답을 쓰면, 그 담당자에게 "📩 팀 리더님 답변 · [과제]"로 쓴 내용 그대로 갑니다(끝에 `/막힘`·`/완료` 안내가 붙음). 막힘 DM에는 "✅ 답장 보냄 (시각)"이 붙고 버튼은 남아서 더 보낼 수 있습니다.
- **`/답장`** (서버 채널·봇 DM): 버튼이 없을 때(전달 동의 없는 막힘, 그 밖의 과제 관련 답) 진행 중인 과제를 골라 같은 방식으로 보냅니다.
- **봇 DM 창에 글로 쓰면 아무 데도 전달되지 않습니다.** 봇은 DM 글을 읽지 않습니다.
- 답장한 날이 기록되어 `npm run metrics`에 "막힘에 1영업일 이내 리더 답장" 참고 지표로 나옵니다.

### 담당자

**저녁 체크인 버튼**

- **[완료]**: 지금 단계를 끝냈다고 기록하고 다음 단계를 알려 줍니다. 마지막 단계면 과제가 완료됩니다.
- **[진행 중]**: 그대로 기록합니다. 마감이 빠듯하면 미리 알려 줍니다.
- **[막힘]**: 입력창에 어디서 막혔는지 적으면 코치가 힌트를 줍니다. 이어서 "팀 리더님께 전달할까요?"라고 물어봅니다.
  - **[팀 리더님께 전달]**: 화면에 보이는 한 줄 요약만 팀 리더에게 갑니다.
  - **[조금 더 해 볼게요]**: 아무것도 보내지 않습니다.

**언제든 완료 알리기: `/완료`**

체크인을 기다리지 않고 지금 단계를 끝냈다고 알립니다. 봇과의 DM 창이나 팀 서버 채널 어디서나 쓸 수 있습니다. 과제가 여러 개면 어느 과제인지 버튼으로 고릅니다. 하루에 두 단계를 끝냈으면 두 번 쓰면 됩니다.

**언제든 막힘 알리기: `/막힘`**

체크인을 기다리지 않고 막힌 곳을 바로 알립니다. 체크인의 [막힘]과 같은 입력창이 뜨고, 힌트를 받은 뒤 팀 리더님께 전달할지 고릅니다. 봇 DM이나 팀 서버 채널 어디서나 쓸 수 있고, 서버 채널에서 쓰면 힌트도 본인에게만 보입니다. 과제가 여러 개면 버튼으로 고릅니다.

**마감 바꾸기 요청: `/마감변경`**

바꾸고 싶은 최종 마감과 이유를 적으면 팀 리더님께 요청이 갑니다. 이유는 적은 그대로 전달됩니다. 승인이나 거절 결과는 DM으로 옵니다. 오늘보다 이전 날짜로는 바꿀 수 없고, 한 과제에 대기 중인 요청은 하나만 둘 수 있습니다.

**기록되는 것**

체크인 상태(완료 · 진행 중 · 막힘)와 막힘의 한 줄 요약만 저장합니다. 막힘 입력창에 쓴 원문은 저장하지 않습니다. 다만 힌트를 만들기 위해 AI(Cloudflare Workers AI)에는 전달됩니다.

### 알아 둘 점

- 공휴일 목록(`src/dates.ts`의 `HOLIDAYS`)이 비어 있으면 공휴일에도 DM이 갑니다.
- 17:00에 봇이 꺼져 있었다면 그날 체크인은 건너뜁니다.
- AI 응답은 30초 안팎 걸릴 수 있습니다. "생각 중"이 떠 있으면 기다려 주세요.
- 명령어가 안 보이면 Discord 앱을 다시 시작하세요.

## 기술 스택

| 영역 | 선택 |
| --- | --- |
| 런타임 | Node 24 LTS + TypeScript (실행 `tsx`, 빌드 `tsc`) |
| Discord | `discord.js` v14, Gateway 상시 접속 (슬래시 명령·버튼·모달·DM) |
| 스케줄 | `node-cron`, `timezone: 'Asia/Seoul'` |
| DB | SQLite (`better-sqlite3`) + `drizzle-orm/better-sqlite3` (마이그레이션 `drizzle-kit`) |
| AI | Cloudflare Workers AI 무료 등급(REST, OpenAI 호환 `/ai/v1/chat/completions`) 기본, Groq 대체(선택) |
| 검증 | `zod` (AI가 만든 단계 초안 JSON 검증) |
| 테스트 | `vitest` (영업일·마감 위험 계산만) |
| 배포 | 회사 서버, Docker (`node:24-slim`) + Docker Compose |

## 결정 사항과 이유

- **Cloudflare Workers 대신 회사 서버의 Node 봇.** Workers는 Gateway 상시 접속이 안 돼 "@코치 한 줄 등록"과 DM 자유 입력을 쓸 수 없고, 슬래시 명령은 3초 안에 응답해야 하며, Cron이 UTC로 고정된다. 서버에서 돌리면 이 제약이 모두 사라진다.
- **Supabase 대신 SQLite.** 사용자 2명, 컨테이너 1개 규모라 별도 DB 서비스가 주는 이점이 없다. 계정과 키 관리만 늘어난다.
- **Drizzle ORM.** 스키마를 TypeScript로 정의하고 타입을 추론해 쓴다. 테이블이 3~4개라 가볍다.
- **AI 기본값은 Cloudflare Workers AI 무료 등급.** 하루 10,000 Neurons 무료(00:00 UTC 초기화), 초과하면 Workers Paid 없이는 오류. 서버라 바인딩 대신 REST로 호출. 일부 대형 모델(kimi-k2.6, glm-5.2 등)은 무료 등급에서 403이라 무료 등급 모델(기본 `@cf/google/gemma-4-26b-a4b-it`)을 쓴다. `GROQ_API_KEY`가 있으면 Workers AI가 과부하·오류·JSON 깨짐일 때 Groq로 넘어간다. 호출부는 `src/ai.ts`의 `chatJson` 하나.
- **Node 24 LTS 런타임.** `discord.js`의 공식 지원 런타임이라 Gateway 안정성 위험이 없다. Bun은 검토했으나 쓰지 않는다. `.nvmrc`와 `engines`를 24로 맞춘다.
- **드라이버는 `better-sqlite3`.** 동기식이라 코드가 단순하다. Node 내장 `node:sqlite`는 아직 실험 단계라 쓰지 않는다.
- **Flue 미적용.** Flue는 도구를 쓰며 스스로 판단하는 자율 에이전트용 하네스(Astro 팀, 실험 단계)다. 이 봇은 순서가 고정된 워크플로에 AI 호출이 세 곳(단계 초안, 힌트·응원, 요약)뿐이라 직접 짠 `ai.ts` 함수로 충분하다. 나중에 에이전트가 코드·문서를 읽고 스스로 조사해야 하면 다시 검토한다.

## 핵심 루프

과제 등록 → 단계 초안 → 팀 리더 확인 → 매일 체크인 → 기록·응원 또는 막힘 지원 → 팀 리더 요약

## 폴더 구조 (계획)

```
src/
  index.ts      봇 시작, Cron 등록, 마이그레이션 실행
  commands.ts   /과제 슬래시 명령, 버튼·모달 처리
  jobs.ts       아침 안내, 저녁 체크인, 팀 리더 요약
  ai.ts         단계 초안, 힌트, 요약
  db.ts         DB 연결과 쿼리 함수 모음
  schema.ts     Drizzle 스키마 (tasks, steps, checkins, members)
  dates.ts      영업일·마감 위험 계산 (테스트 대상)
drizzle/        생성된 마이그레이션 SQL
data/           SQLite 파일 (볼륨 마운트)
Dockerfile
docker-compose.yml
.env.example
```

## 운영 주의사항

- **DB 볼륨 마운트 필수.** `docker-compose.yml`에서 `./data:/app/data`로 연결한다. 컨테이너 안에 두면 이미지를 다시 빌드할 때 데이터가 사라진다.
- **백업은 직접 챙긴다.** 서버 cron으로 하루 한 번 `sqlite3 data/pacer.db ".backup 'backup/pacer-날짜.db'"`를 실행한다. 파일 복사는 쓰는 도중 깨질 수 있으니 `.backup` 명령을 쓴다. 회사 서버의 백업 정책에 `data/`가 포함되는지 확인한다.
- **마이그레이션 폴더를 이미지에 복사한다.** `drizzle/`가 없으면 시작할 때 `migrate()`가 실패한다.
- **베이스 이미지는 `node:24-slim`.** `better-sqlite3`는 네이티브 모듈이라 alpine(musl)에서 빌드 문제가 생기기 쉽고, slim(glibc)이 안전하다. 개발 PC와 서버 CPU 구조가 다르면 이미지는 서버에서 빌드한다.
- **DB 연결 직후 `PRAGMA journal_mode = WAL`, `PRAGMA foreign_keys = ON`을 실행한다.**
- **재시작 대응.** 시작할 때 오늘 체크인이 이미 나갔는지 DB로 확인하고, 놓쳤으면 한 번만 보낸다.
- **Discord 개발자 포털에서 Message Content Intent를 켠다.** "@코치 한 줄 등록"에 필요하다.
- **방화벽.** 아웃바운드로 Discord, `api.cloudflare.com`, (대체를 쓰면) `api.groq.com`에 나갈 수 있어야 한다. Gateway 방식은 인바운드 포트가 필요 없다.
- **데이터 보관.** 체크인 원문은 저장하지 않고 상태와 요약만 남긴다. 팀 리더에게도 원문은 보내지 않는다.

## 개발 순서

1. ✅ 봇 접속, `/과제` 명령, AI 단계 초안, 팀 리더 [이대로 전달] [수정] [취소] 버튼. [수정]은 제목·최종 마감·단계(한 줄에 "제목 - YYYY-MM-DD")를 입력창에서 직접 고치고, 형식이 틀리거나 마감보다 늦은 줄이 있으면 초안을 그대로 두고 알려 준다. [취소]는 초안을 지우고 담당자에게 아무것도 보내지 않는다. 이미 처리된 초안의 버튼은 동작하지 않는다.
2. ✅ 저녁 체크인: 평일 17:00 KST, 과제마다 DM 한 통. [완료]는 지금 단계를 끝내고 다음 단계를 안내, [진행 중]은 마감 위험이면 경고, [막힘]은 입력창 → AI 힌트, 팀 리더용 한 줄 요약만 저장 (`src/jobs.ts`)
   - `/완료`: 담당자가 체크인을 기다리지 않고 지금 단계 완료를 직접 등록. 봇 DM에서도 사용 가능(전역 명령). 과제가 여러 개면 버튼으로 고름. 등록하면 그날 저녁 체크인은 보내지 않는다.
   - `/현황`: 팀 리더 전용. 진행 중인 과제를 막힘·응답 없음(영업일 2일 이상 체크인 없음)·주의(마감 위험 또는 단계 목표일 지남)·순조로움으로 묶어 보여 준다. 항목마다 진행 단계, 마지막 체크인 날짜와 상태, 마감 위험 근거를 표시. 막힘 요약 문구는 담당자 동의 흐름(3단계) 전까지 넣지 않는다. 아침 요약이 같은 함수(`statusReport`)를 쓴다.
3. ✅ 아침(평일 09:00 KST): 팀 리더에게 `statusReport` 개인 DM, 담당자에게 오늘 할 단계 DM. 막힘은 AI 힌트 뒤 [팀 리더님께 전달] 동의를 받은 경우에만 한 줄 요약을 리더에게 바로 DM하고 아침 요약·`/현황`에도 표시(`checkins.shared`). 무응답은 저녁 체크인이 매일 다시 묻고, 영업일 2일 이상이면 요약에 "응답 없음"으로 표시.
4. Dockerfile과 Compose로 서버 배포

## MVP 범위 밖

- 팀원 전체 적용 (실습생 2명으로 2주 운영 후 확대)
- 팀 리더 여러 명. 지금은 `LEADER_ID` 한 명. 늘릴 때 할 일: `LEADER_ID`를 쉼표 구분 `LEADER_IDS`로 바꾸고, `tasks`에 `leader_id` 컬럼을 추가해 맡긴 사람을 기록하고(기존 행은 현재 리더 ID로 채움), 아침 요약·막힘 보고를 그 리더에게만 보낸다.
- 웹 대시보드, GitHub·이슈 트래커 연동
- 인사 평가·성과 점수화, 코드 리뷰 자동화
- DM 자유 입력 답장 (서버라 가능하지만 MVP는 버튼과 입력창으로 시작)

## 나중에 할 것

- **봇 DM 자연어 처리.** `DirectMessages` intent + `Partials.Channel` 추가(봇 DM은 Message Content Intent 불필요). AI가 의도(완료·진행 중·막힘·질문)와 과제를 JSON으로 분류하고, 상태를 바꾸는 의도는 확인 버튼("완료로 기록할까요? [네] [아니요]")을 거친 뒤 기록. 버튼·`/완료`·`/현황`은 AI 실패 시 대체 경로로 유지. 원문은 저장하지 않고 메시지 단위로 처리. 팀 리더 `/과제`는 이름↔계정 매핑이 필요해 슬래시 명령 유지.
- 같은 날 체크인은 하나만 남아서, 낮에 막힘을 기록하고 저녁에 [진행 중]을 누르면 주간 리포트의 "자주 막힌 단계"에서 빠진다.
- 무응답 시 "다음 날 한 번만" 재질문 후 중단 (지금은 답할 때까지 매일 저녁 질문). 체크인 발송 기록이 필요.
- 주말 날짜를 코드로 보정.
- 한 과제를 여럿이 나눠 하는 공유 방식 (지금은 사람마다 복사만 지원).

## 환경 변수 (`.env`)

`DISCORD_TOKEN`, `DISCORD_APP_ID`, `DISCORD_GUILD_ID`, `LEADER_ID`(팀 리더 Discord ID), `CF_ACCOUNT_ID`, `CF_API_TOKEN`(Workers AI 권한), `CF_MODEL`(기본 `@cf/google/gemma-4-26b-a4b-it`), `GROQ_API_KEY`(선택, 대체용), `GROQ_MODEL`(기본 `qwen/qwen3.8-27b`), `DATABASE_PATH`(기본 `data/pacer.db`), `WORK_START`·`WORK_END`(기본 `09:00`·`18:00`, 이 밖의 알림은 소리 없이)

## 실행

```bash
npm install
cp .env.example .env   # 값 채우기
npm run dev            # 개발
npm run dev -- --checkin-now   # 시작하자마자 저녁 체크인을 한 번 보냄 (테스트용, 파일 저장으로 재시작될 때마다 다시 보냄)
npm run dev -- --morning-now   # 시작하자마자 아침 요약·안내를 한 번 보냄 (테스트용)
npm test               # 영업일·마감 위험 계산 테스트
npm run db:generate    # schema.ts 변경 후 마이그레이션 생성
docker compose up -d --build   # 서버 배포
```

## 성공 기준 (실습생 2명, 2주)

- 단계 초안의 80% 이상이 팀 리더 수정 1회 이내로 확정
- 체크인 응답률 80% 이상 (영업일 10일 중 8일)
- 막힘이 생긴 뒤 팀 리더가 알기까지 1영업일 이내
- 마감을 놓친 과제 0건, 위험하면 최소 2일 전 경고
